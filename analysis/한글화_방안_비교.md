## 1. 방안 1 — ROM 크기 유지, 한글 약 900자

### 1-A. 코드 수정 없이 (순수 데이터 교체)

- 한글은 `F0~F2 xx` 768칸뿐입니다. 900자가 아니라 **768자가 상한**입니다.
- 텍스트는 원래 뱅크와 원래 바이트 수 안에 들어가야 합니다.
  → 한국어 음절 수를 일본어의 절반 수준으로 줄여야 하므로 **대폭 축약 번역**이 됩니다.
- 장점:
  - 작업이 가장 단순합니다(폰트 교체 + 테이블 + 재삽입 도구).
  - 원본 코드를 건드리지 않아 버그 위험이 낮습니다.
- 단점:
  - 문장 축약이 심합니다.
  - 768자에 없는 음절은 다른 표현으로 바꾸거나 오자를 감수해야 합니다.
  - 고유명사(카미유, 쥬도, 시브크, 크와트로…)에 쓰이는 드문 음절이 많아 768칸이 빠듯합니다.

### 1-B. 900자 + 1바이트 한글 (코드 수정 필요)

- 1바이트 코드 `40~DF`(160칸)를 **자주 쓰는 한글 음절**에 할당하고 16px 폭으로 그리게 고칩니다.
  2바이트 768칸을 더하면 약 900자가 됩니다.
- 상위 160음절이 한국어 텍스트의 대략 60%를 차지한다고 가정하면 예상 크기는 원본 대비 **+5~15%** 정도입니다.
  - 이 비율은 일반적인 한국어 통계로 잡은 추정치입니다. 번역문으로 실측해야 합니다.
- 그래도 넘치는 부분은 DTE(2글자 압축)나 약간의 축약으로 맞춥니다.
- 결국 **텍스트 출력 루틴 ASM 수정이 필요**합니다(1바이트 글자 폭·폰트 주소 변경).
  "ROM 크기 유지"의 이점은 남지만, "코드 무수정"의 이점은 사라집니다.

## 2. 방안 2 — ROM 확장, 한글 2,350자 (KS X 1001 완성형)

- ROM을 12Mbit → **16Mbit(2MB) LoROM**으로 확장합니다. 뱅크 $B0~$BF 512KB가 새로 생깁니다.
- 폰트: 2,350자 × 32바이트 = 75,200바이트 (2.3뱅크).
- 인코딩: 2바이트 접두를 `E8~EF` + `F0~F2` = 11 × 256 = 2,816칸으로 늘립니다.
  `E8~EF`는 대본에서 쓰이지 않는 것을 확인했습니다.
  → 글자 코드 → 폰트 주소 계산 부분만 고치면 됩니다.
- 텍스트 재배치:
  - 대사가 **블록(테이블+문자열) 단위로 뱅크 안에서 완결**되어 있습니다.
  - 블록을 통째로 새 뱅크로 옮기고, 블록의 뱅크를 정하는 코드만 고치면 16비트 포인터 구조를 그대로 쓸 수 있습니다.
  - 가장 큰 블록(0x48000, 약 19KB)도 +45%면 약 28KB로 한 뱅크(32KB)에 들어갑니다.
- 장점:
  - 원문에 충실한 번역이 가능합니다. 오자나 억지 대체어가 필요 없습니다.
  - 글자 수 제한을 의식하지 않고 번역할 수 있습니다.
- 단점:
  - ASM 작업 범위가 넓습니다(폰트 주소 계산, 블록 뱅크 선택, 코드에서 직접 참조하는 프롤로그·엔딩).
  - 에뮬레이터 디버거로 루틴을 추적해야 합니다.
  - 확장 ROM은 일부 구형 카피어·플래시카트에서 설정을 확인해야 합니다. 2MB LoROM이라 대부분 문제는 없습니다.

## 3. 비교

| 항목 | 1-A (무수정 768자) | 1-B (900자+ASM) | 2 (확장 2,350자) |
|---|---|---|---|
| 번역 품질 | 낮음 (절반 수준 축약) | 중간 (약간 축약·대체어) | 높음 |
| 한글 글자 수 | 768 | 약 928 | 2,350 |
| ASM 수정 | 없음 | 중간 (출력 루틴) | 중~대 (출력 루틴 + 뱅크 선택) |
| ROM 크기 | 1.5MB | 1.5MB | 2MB |
| 기술 위험 | 낮음 | 중간 | 중간 |
| 번역 작업 난이도 | 높음 (분량 맞추기) | 중간 | 낮음 |
| 수정·유지보수 | 어려움 | 보통 | 쉬움 |

## 4. 제안

**방안 2(ROM 확장 + 2,350자)를 권장합니다.**

1. 방안 1도 900자를 쓰려면 결국 출력 루틴 ASM을 고쳐야 합니다.
   ASM을 고친다면, 거기에 포인터 뱅크 처리를 조금 더 하는 것이 방안 2의 추가 비용입니다.
2. 대사가 블록 단위로 뱅크 안에서 완결되어 있어, 블록을 통째로 옮기는 방식이면 재배치 비용이 예상보다 작습니다.
3. 방안 1-A는 코드 수정이 없지만, 번역 분량을 절반으로 줄여야 해서 번역 품질 손실이 너무 큽니다.

### 진행 순서 제안

1. 에뮬레이터 디버거(Mesen2 등)로 **글자 코드 → 폰트 주소 계산 루틴**과 **블록 뱅크 선택 루틴** 위치를 찾습니다.
   이 두 곳의 난이도를 보고 최종 결정합니다(방안 1-B와 2의 공통 선행 작업).
2. 추출·삽입 도구를 만듭니다(블록 단위 재배치, F9/F7 포인터 갱신 포함).
3. 한글 폰트(12×12)와 테이블을 만듭니다.
4. 시스템 텍스트(이름·무기명·메뉴)는 칸 수 제한 안에서 별도로 처리합니다.

어느 방안이든 1번은 공통입니다. 1번 결과를 보고 확정해도 늦지 않습니다.
